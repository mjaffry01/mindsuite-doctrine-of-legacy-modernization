How MindSuite studies your infrastructure

A third team of 13 agents studies where the system runs, the way an experienced infrastructure architect would: first the facts from your inventories, then the role of each server, then the migration plan. It works from exports your infrastructure team produces with read-only tools; it never logs in to a server. Every claim points to a line in an export and is checked before a person on your side confirms it.

Four rules the whole system follows

Inventories onlyAgents read VM lists, Kubernetes and cloud inventories, connection lists and infrastructure-as-code files. No business data.
Never connected to your serversYour team runs the read-only exports; the agents only read the files.
Every claim is citedEach finding points to the export file and line, or to the findings it is built on.
People decideAgents propose. Your infrastructure team confirms, corrects or rejects each result.

The goal of the infrastructure analysis

Turn your inventories into a validated picture you can plan the move on: what the system runs on, what is out of support, what talks to what and therefore must move together, where it is fragile, and how and in which waves to migrate. It ends in the Infrastructure analysis report.

What it runs onServers, VMs, Kubernetes, cloud, sizes, platforms.
What is out of supportOperating systems, hypervisor, software, container images.
What moves togetherWho talks to whom, outside partners, shared hubs, move groups.
How to migrateStrategy per host, waves, the approach and target sizing.

What inventories alone cannot tell, and how it is handled

How busy each server really is, who owns a server outside the inventory, whether a powered-off VM is a standby, and what people do on servers they log in to. The agents do not guess these: they become questions for your infrastructure team.

One finding, end to end

  1. The estate reader reads the RVTools export: 7 VMs on vSphere 6.7, one powered off. It also reads the connection lists of three servers.
  2. Dependencies resolves the addresses to server names: app-prod-01 and app-prod-02 talk to db-prod-01 on port 1521 (Oracle), and batch-prd-01 sends files to 203.0.113.10 over SFTP, a server outside the inventory.
  3. Lifecycle finds that four of the five servers in that group run an unsupported OS, and that vSphere 6.7 itself is out of support. Security & resilience finds Telnet and AJP between servers and a single database server.
  4. If you allow it, the roles agent confirms db-prod-01 is the production database and mon-01 is shared monitoring.
  5. The migration assessment puts the five connected servers in one wave, marks old-report-01 to retire and mon-01 to exclude, and suggests replatforming the database and application servers.
  6. Your infrastructure team confirms, and tells who owns the SFTP partner, which becomes a dependency to keep open during the move.

What is running today

All 13 agents run in the same MindSuite agent backend as the other teams. In MindSuite, open Record evidence → Environment & infrastructure → Run the infrastructure agent team, choose the export files, and watch the 9 steps run.

12 rule-based agents always run and nothing leaves the backend machine. The roles agent runs only with a Claude API key on the backend and your consent for that run; it sends host names, OS, sizes, software and connection summaries, never credentials.

Still to come: utilisation data (CPU and memory use) for right-sizing, reading vCenter or cloud APIs directly through the Discovery Collector, and linking servers to the code and database teams' findings.
