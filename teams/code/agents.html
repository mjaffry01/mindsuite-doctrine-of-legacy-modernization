How MindSuite studies your code

A team of specialised agents reads your code the way an experienced modernization team would: first the facts, then the meaning, then the assessment. Every claim is checked before a person on your side confirms it. This page shows each agent, how they work together, and what is already running today versus planned. The database has its own team: how MindSuite studies your database.

Four rules the whole system follows

Read-onlyAgents read a copy of your code. Nothing is executed, changed or connected to production.
Facts before opinionsExact tools (parsers) find facts. Language models only explain and connect them.
Every claim is citedEach finding points to a file and line, a table or a document, with its basis and confidence.
People decideAgents propose. A named person on your side confirms, corrects or rejects each result.

The goal of the code analysis

Turn your code into a validated picture you can decide on: what the system is made of, how it works for the business, where it is fragile, and where to start modernizing. It ends in two results, the Code analysis report and the Business story. Every statement points to its evidence, and is confirmed by a named person on your side.

What it is made ofTechnology, modules, data, interfaces, platform.
How it worksBusiness rules, journeys, events, vocabulary.
Where it is fragileCoupling, shared tables, missing tests, risks, secrets.
Where to startExtractability, effort, seams and order.

How the analysis runs, step by step

Each step builds on the one before. Steps 3 and 5 run many agents in parallel, one work package per module. Click an agent name to see it in the diagram.

Large codebases and coverage

The orchestrator splits the code into work packages per module and tracks coverage: which files and modules each agent has analysed. Files no agent can read yet (an unsupported language, generated or binary files) are listed as gaps, never silently skipped. The report states its coverage, e.g. "312 of 340 files analysed; 28 PowerBuilder files waiting for the specialist".

What code alone cannot tell, and how it is handled

Why a rule exists, whether it is still wanted, which features are really used, and what people do outside the system. The agents do not guess these. The verifier turns them into questions for your experts, and telemetry (if provided) shows which code paths are actually used.

How the agents communicate

Agents do not chat freely with each other. They exchange five kinds of messages through the orchestrator and a shared evidence store, so every step is recorded and can be traced.

1 · TaskOrchestrator → agent

"Analyse module grading: files, tables, rules." Each task has a scope and a deadline.

2 · FindingAgent → evidence store

A claim with citation, basis and confidence, e.g. "GRADE_RESULT is written only by grading (GradeCalc.java:41)".

3 · Hand-offAgent → orchestrator

"These 40 files are COBOL; send them to the legacy specialist." The orchestrator re-plans.

4 · VerificationVerifier → evidence store

Accepted, rejected (citation does not support it) or conflict (two agents disagree).

5 · Question for an expertVerifier → people

"Is the 2% late-delivery penalty still wanted? It is in SettlementService.java:88 but not in the process document."

Example of a finding as stored (simplified):

{
  "agent": "business-rules",
  "claim": "Grade A requires moisture below 14% and defects under 2%",
  "citation": "src/main/java/com/harvestlink/grading/GradeCalc.java:212-219",
  "basis": "observed in code",
  "confidence": 0.86,
  "context": "Grading",
  "verified": "accepted",
  "status": "waiting for a person to confirm"
}

One finding, end to end

  1. Inventory finds 312 Java files, a Maven build and the commit being analysed.
  2. The orchestrator splits the work by module and sends tasks to the fact agents in parallel.
  3. Structure finds the module grading; Data access finds it writes GRADE_RESULT; Quality flags GradeCalc.java as the most complex file.
  4. Because it is complex and business-critical, the orchestrator asks the Business-rules agent to read GradeCalc.java. It writes the rule in plain language with the exact lines.
  5. The Verifier re-opens lines 212–219, confirms they say what the claim says, and checks the process document. The document says 15%, so it raises a conflict and a question for the domain expert.
  6. The Report writer includes the rule and the open question in the Code analysis report.
  7. Your domain expert answers in MindSuite: "14% is correct; the document is outdated." The rule becomes Confirmed, with their name and date in the history.

Which models are used

Not one model per agent. Models are chosen by the difficulty of the task, and each agent's model is a setting that can be changed after testing on your code.

TierModelUsed byWhy
0 · No modelExact parsers and rulesOrchestrator, Inventory, Supply chain, Structure, Data access, Interfaces, Security, Quality, Platform & config, Legacy specialists, Assessment, and the citation checks of the VerifierFacts must be exact and repeatable
1 · FastClaude Haiku 5.5Reserved for bulk summarising of very large codebases (not used yet)High volume, simple tasks
2 · BalancedClaude Sonnet 5.5Verifier (second opinion on every model claim), Report writerUnderstanding code relationships within clear limits
3 · StrongestClaude Opus 5.5Business rules, Domain & processHard reasoning; mistakes here would mislead decisions
VerifierA different model or prompt from the agent it checksVerifierAvoids repeating the same blind spot; re-reads the cited lines itself

What is running today

All 15 agents run in the MindSuite agent backend, a small service you run next to your code (on your machine or a server in your network). In MindSuite, open 02 Code analysis → Run the full agent team, choose the code folder or zip, and watch the 9 steps run. The code is read, never executed, and is not stored by the backend.

The 11 rule-based agents always run, and nothing leaves the backend machine. The Claude-powered steps (business rules, the business story, the verifier's second opinion and the written summary) run only if the backend has a Claude API key and you tick the consent box for that run. Even then, only the files the orchestrator picks are sent, lines that may hold a password or key are removed first, and every request is listed in the result.

Still to come: licences and a vulnerability database lookup for dependencies (needs your OK to send dependency names outside), and specialists for Oracle Forms and ABAP. A quick browser-only scan (no backend) is still available on the Source code card.
